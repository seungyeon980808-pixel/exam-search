# 검색 시도 후 대기와 화면 단절을 줄인 2차 개선

2026-10-08, `codex/exam-library-fast`. 1차 개선은 `FAST_LIBRARY_OPERATIONS.md`에 기록되어 있다. 여기의 개선 전은 원래 공개 버전이 아니라 **1차 개선 완료 상태**다. 같은 별도 작업 트리를 사용했고 main 병합·push·태그·배포는 하지 않았다.

## 사용자가 느끼는 대기를 줄인 변경

1. 검색과 변환 자료를 분리했다. 과목별 검색 전용 자료는 전체 합계 **25,213,576바이트**다. 기존 상세 자료 50,744,716바이트의 도형·좌표·변환 정보까지 읽으며 검색 문자열을 만들던 비용을 줄였다. 검색 문자열은 빌드 시 정규화하며, 같은 문자열 안의 범위로 제목·태그·본문 관련도 점수를 계산한다. 본문을 중복 저장하지 않는다.
2. 조건이 바뀌면 이전 검색 RPC와 불필요한 자료 준비를 취소한다. 현재 요청을 먼저 처리하고 입력 중의 준비는 낮은 우선순위로 처리한다. 요청들이 공유하는 자료는 사용자가 남아 있는 동안 취소하지 않는다. 다운로드·준비 동시 작업 수는 2개다. 입력 중 준비와 제출된 검색이 같은 과목 색인을 중복 생성하지 않도록 공유한다.
3. 과목 선택 후에는 해당 과목을 유휴 시간에 준비한다. 검색창에 실제로 글자를 입력하면 현재 검색 범위의 자료를 준비한다. 아무 입력도 하지 않은 랜딩 화면에서는 전체 검색 자료를 가져오지 않는다. 사용자가 다른 과목을 선택하면 이전 범위의 준비를 중단한다.
4. 검색 시작과 동시에 상태를 표시하고 이전 결과에 '갱신 중 · 이전 결과'를 표시한다. 입력과 필터는 계속 조작할 수 있다. 갱신 중인 이전 목록은 선택이 잠시 제한되며, 새 결과는 준비가 완료된 뒤 한 번에 교체한다. 실패하면 이전 결과와 작성 중인 검색어를 유지하고 재시도할 수 있다. 이미 선택한 문항이 새 결과에도 있으면 오른쪽 문항을 다시 초기화하지 않는다. 취소된 문항 요청을 오류로 표시하지 않는다.

## 실제 클릭부터 결과 표시까지

- 같은 Apple M5, Chromium 153.0.8010.12, 1440×900, Python 로컬 서버 8851.
- 19,760문항·822 PDF·21개 과목 코드의 실제 자료를 사용했다.
- 개선 전후 각각: 과목 지정 검색과 전체 검색, 첫 방문과 재방문을 **각 5회** 측정했다. 합계 40회다. 재방문은 같은 브라우저 컨텍스트의 새 페이지이며 브라우저 캐시를 유지했다.
- 검색어는 `전자기파`. 지정 조건은 물리학Ⅰ·2025학년도·수능이다. 첫 목록/랜딩 준비 후 입력을 한 번에 채우고 즉시 제출했다. 클릭 측정 시작은 form 제출 직전이고 완료는 실제 결과와 '본문 검색 완료'가 표시된 시점이다.
- 최종 성능 측정은 다른 QA 실행이 끝난 뒤 진행했다. 외부 PDF 다운로드는 검색 측정에 포함하지 않는다.
- 표의 수치는 **중앙값 / 최댓값, ms**이다.

| 검색 조건 | 방문 | 1차 개선 상태 | 이번 개선 후 |
|---|---|---:|---:|
| 물리학Ⅰ 지정 | 첫 방문 | 24.2 / 37.1 | 21.2 / 23.9 |
| 물리학Ⅰ 지정 | 재방문 | 24.2 / 24.8 | 6.5 / 7.1 |
| 전체 과목 | 첫 방문 | 523.3 / 590.7 | 380.1 / 420.5 |
| 전체 과목 | 재방문 | 374.2 / 391.6 | 272.4 / 354.7 |

전체 첫 검색 중앙값은 약 27%, 재방문은 약 27% 줄었다. 과목 지정 첫 검색은 이미 빨랐기 때문에 중앙값 개선은 작다. 재방문 지정 검색은 준비를 입력·조건 선택과 겹쳐 처리해 약 73% 줄었다.

전체 검색에 사용한 검색+목록 자료는 **59,539,378→34,008,238바이트**, 약 43% 감소했다. 물리학Ⅰ 지정 검색은 **2,324,192→1,544,634바이트**, 약 34% 감소했다. 이 값은 응답 Content-Length 합계이며 카탈로그·HTML·CSS·문항 미리보기는 제외한다. Brotli/gzip 전송 크기를 측정한 값은 아니다. 새 페이지의 브라우저 HTTP 캐시 응답에서 Content-Length가 생략되어 0으로 기록된 경우에도 영속 캐시를 읽고 검증하는 비용은 실제 경과 시간에 포함된다.

기존 결과가 있었던 지정 검색에서는 개선 전 10회 모두 목록이 비는 DOM 관찰이 있었고, 개선 후 10회 모두 없었다. 이는 화면의 시각적 공백 시간 자체를 재는 PaintTiming이 아니라, 결과 교체 중 DOM에 문항 카드가 없었던 상태의 발생 여부다. 별도 지연 검수에서도 이 동작을 확인했다.

## 입력하는 동안 준비하는 경우

별도 개선 후 측정에서 검색어 4글자를 글자당 150ms로 입력한 다음 제출했다. 각 조건·방문에 5회씩, 총 20회다. 타이핑에 사용한 시간은 아래 클릭 후 경과 시간에 더하지 않았다. 개선 전의 같은 타이핑 측정은 없으므로 개선 전후 비율을 제시하지 않는다.

| 검색 조건 | 첫 방문 | 재방문 |
|---|---:|---:|
| 물리학Ⅰ 지정 | 3.3 / 15.3 | 3.2 / 16.6 |
| 전체 과목 | 61.7 / 64.1 | 49.5 / 49.9 |

대기 시간을 숨기기 위해 고정 지연을 추가한 방식이 아니다. 검색 준비를 사용자가 조건을 고르거나 입력하는 시간과 겹쳐 처리한 것이다. 입력이 빠르거나 자료 수신이 느리면 제출 후에도 준비가 필요하다.

## 검수와 품질 보존

- 337개 테스트 통과. 전체 19,760문항의 정규화 검색 문자열, 공백 제거 문자열, 제목·태그·본문 점수 문자열이 기존 엔진과 동일함을 확인했다. 대표 단어와 복합 검색의 결과 순서도 비교했다.
- 모든 변환 상세 자료 필드는 원본과 깊은 동등성 비교를 통과했다. `/api/question`과 변환·내보내기는 원래 상세 자료를 사용한다. 검색용 자료로 원본 품질을 대체하지 않는다.
- Chromium·WebKit × 1440·768·375px: 랜딩 가벼운 로딩, 단원 범위, 페이지 앞뒤 이동, 빠른 조건 변경, 검색어 유지, 가로 넘침 없음.
- 실제 12개 과목의 검색 수·순서가 기존 엔진과 동일했다.
- 검색 자료를 지연시킨 상태에서 이전 결과·작성 중인 검색어·입력 가능 상태가 유지됐다. 실패 후 이전 결과가 남고 재시도에 성공했다.
- 전체 검색의 이전 다운로드 2개를 무기한 지연시킨 뒤 화학Ⅰ으로 전환했다. 두 요청이 실제 취소됐고 새 결과는 Chromium **29ms**, WebKit **45ms**에 표시됐다. 이는 취소 동작을 검증한 인위적 지연 시나리오의 관찰값이며 일반 검색 성능 평균으로 사용하지 않는다. 나중에 이전 응답을 풀어도 새 결과가 유지됐다.
- 원본 지연 시 마지막 선택 문항·125% 확대·60px 스크롤 유지, 시험지 8개 빠른 전환에서 다운로드 제한 2개와 마지막 파일 유지, 편집 중 카탈로그 변경 시 문서·90% 확대·미저장 경고 유지, 저장소 접근 불가 시 네트워크 대체 검수 통과.
- 실제 HWPX 편집·내보내기: 입력한 글자, 본문, 네이티브 수식 7개, 미저장 경고 유지.
- 기존 PDF QA: 1280·768·375px에서 고해상도 문항·4페이지 PDF·스크롤 통과.
- Safari에서도 실제 키워드 검색 결과를 확인했다.

## 한계

처음 전체 검색을 즉시 실행하면 이번 로컬 환경에서도 약 380ms가 걸린다. 느린 네트워크와 저사양 장치에서는 더 길어질 수 있다. 이번 결과를 모든 사용자의 100ms 이하 응답을 보장하는 수치로 해석하지 않는다. 대신 준비 중에도 입력과 조건 변경을 막지 않고, 이전 결과와 편집 내용을 유지하며, 최신 요청이 오래된 요청 뒤에서 대기하지 않게 한다.

단원 매핑 누락·읽기 어려운 PDF 본문·복잡한 문항의 기존 한글 복원 한계는 별도 품질 과제다. 인터넷상의 공개 배포 사이트는 이번 작업으로 바뀌지 않았다.

## 유지보수

현재 카탈로그 셰마는 `exam-browser-v3`, 영속 캐시는 `exam-library-catalog-v3`, 런타임 모듈 버전은 `library-20261008-3`이다. 카탈로그와 63개 자료 파일(21개 과목 × 목록·검색·상세)을 함께 관리한다. 원본이 바뀌면 `npm run build:catalog`로 다시 생성하고 전체 필드·검색 동등성 검사를 실행한다. 빌드 시의 검색 정규화는 로컬 코드 처리이며 AI 호출은 없다.

```sh
npm run build:catalog
npm test
npm run qa:library
npm run qa:library-state
npm run qa:search-response
npm run measure:search-response -- after
npm run measure:search-response -- typed typing
```

서버는 기존과 같이 `python3 -m http.server 8851 --bind 127.0.0.1`로 실행한다. `EXAM_SEARCH_URL`로 검수 URL을 바꿀 수 있다. 측정 도구는 QA와 동시에 실행하지 않는다.

로컬 증거는 `_work/performance/search-before.json`, `search-after.json`, `search-summary.json`, `search-typed.json`, `search-typed-summary.json`, `ui/search-response-results.json`에 있다. 상세 QA 로그·화면·HWPX는 같은 폴더에 있다. `_work`와 브랜치 구조 HTML은 배포·게시하지 않는다.
