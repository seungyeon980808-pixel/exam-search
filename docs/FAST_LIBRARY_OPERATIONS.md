# 기출 라이브러리 초기 로딩·검색 개선 기록

이 문서는 1차 개선의 측정 기록이다. 현재 검색 방식·셰마·캐시·자료 파일 수와 추가 검수는 [2차 검색 반응성 개선](SEARCH_RESPONSIVENESS.md)을 따른다.

검수일: 2026-10-08. 작업 브랜치: `codex/exam-library-fast`.
비교 기준 커밋: `991d1113f5d00f55027bb9a1262cb3fd6539b6ae`.
기존 작업을 보존하기 위해 별도 작업 트리에서 구현했다. main 병합, push, 태그, 배포는 실행하지 않았다.

## 병목과 적용 방식

기존 화면은 약 50.75MB의 전체 문항 JSON을 가져와 메인 스레드에서 파싱하고 검색용 문자열을 준비한 후 목록을 표시했다. PDF 모듈도 첫 화면에서 불러왔다. 첫 목록이 나타나기 전 146ms 중앙값의 긴 작업이 발생했다. 원본 PDF 준비는 외부 공개 게이트웨이의 응답·다운로드와 PDF 렌더링 대기가 주로 차지했다.

5E의 `STABILITY_FOLLOWUP_OPERATIONS.md`를 읽기 전용으로 참고하여 다음을 적용했다.

- 1.04MB 기본 목록과 과목별 가벼운 목록을 먼저 사용한다. 물리학Ⅰ 검색 목록 준비에는 합계 1,563,278바이트가 필요하다. 기존 전체 문항 JSON 대비 약 97% 적다. 시험지 기본 목록은 미리 계산한 파일별 문항 수·프로필·첫 페이지를 사용한다.
- 과목별 본문은 키워드 검색, 상세 문항 또는 변환 요청 시 준비한다. 검색 문자열 준비와 검색은 Web Worker로 분리했다. 준비 중에도 입력값을 유지하고 준비·실패·재시도 상태를 표시한다.
- PDF 및 한글 편집기는 필요한 시점에 불러온다. 기존 문항 미리보기는 바로 조작할 수 있고 고해상도 원본으로 교체할 때 선택·확대·스크롤을 유지한다.
- 캐시한 목록을 먼저 표시하고 현재 목록을 뒤에서 확인한다. 변경된 목록은 새로고침 안내로만 제공하며 열린 문항과 편집 문서를 자동으로 교체하지 않는다. 본문 자료는 바이트 수와 SHA-256을 검증하고 손상된 캐시는 다시 가져온다. 저장소 접근 불가 시 네트워크로 동작한다.
- 원본 PDF 다운로드 2개, 래스터 렌더링 2개, 자료 준비 2개로 동시 처리를 제한했다. 이전 선택의 화면 반영을 취소하고 대기 중인 불필요한 요청을 건너뛴다.
- PDF 문서·바이트는 사용 중인 소비자를 보호하며 유휴 문서 4개로 제한한다. 완성된 페이지 래스터 2개, 상세 과목 캐시 4개, 검색 결과 8개를 보관한다. 문항 DOM은 현재 페이지와 인접 페이지만 유지하고 제거된 Blob URL을 해제한다. 전체 검색을 요청한 경우의 최소 검색 문자열 색인은 별도로 유지한다.

## 화면 변경

- 검색창 최대 너비 380px. 과목 → 세부 과목 → 연도·시험 → 키워드 순서로 배치하고 키보드 이동 순서도 맞췄다.
- 단원·성취기준은 과목, 연도, 시험 및 국어·수학 선택과목 조건에 맞춰 제공한다. 과목이 지정되지 않으면 단원 선택을 비활성화한다. 매핑된 단원이 없는 자료에는 키워드 검색 안내를 표시한다. 기존 복합 단원 URL도 유지한다.
- 문항을 한 화면에 6·9·18·36개씩 볼 수 있다. 선택값은 URL과 로컬 설정에 남는다. 좁은 화면에서는 추가 메뉴에서 변경한다. 시험지는 별도로 12개씩 표시한다.
- 첫 진입 시 과목별 시작 카드, 실제 자료 규모, 전체 시험지 둘러보기를 제공한다. 기존 검색 URL과 문항 직접 링크는 유지한다.

## 측정 조건

- 같은 Mac Apple M5, Chromium 153.0.8010.12, 1440×900, Node v26.8.1, Python 3.9.6 정적 HTTP 서버.
- URL: `http://127.0.0.1:8851/?group=science&subject=p1&year=2025&month=11`.
- 실제 자료: 19,760문항, 822 PDF, 21개 과목 코드. 원본 `data/questions.json`은 50,745,033바이트이며 변경하지 않았다.
- 개선 전·후 각각 새 브라우저 컨텍스트 5개. 각 컨텍스트에서 첫 방문 1회와 동일 캐시를 유지한 새 페이지 재방문 1회씩 측정했다. 개선 전후 총 20회다.
- 첫 화면은 FCP, 조건 조작은 필터 옵션이 준비된 시점, 목록 조작은 실제 결과 카드와 문항 수가 표시된 시점이다. 전체 검색 준비는 21개 과목의 본문 색인을 모두 요청한 완료 시점이다. 원본 준비는 목록 첫 문항 클릭부터 고해상도 Blob 이미지가 로드된 시점이다. 나머지 단계는 탐색 시작부터 측정한다.
- 다른 QA 실행이 끝난 뒤 최종 측정을 진행했다. 원본은 실제 공개 게이트웨이를 사용했으며 네트워크 속도를 고정하지 않았다. 신규 브라우저 컨텍스트는 브라우저 캐시를 비우지만 외부 게이트웨이의 캐시까지 초기화하지 않는다.
- 원본 준비는 비교 양쪽 모두 전체 검색 준비가 끝난 뒤 측정했다. 실제 앱 첫 화면에서는 전체 본문 검색 준비를 강제하지 않는다.

### 해석과 한계

목록 조작 가능 시점은 첫 방문 약 79%, 재방문 약 83% 단축했다. 첫 화면의 단순 표시 자체는 개선되지 않았다. 준비된 검색 요청은 이미 1ms 안팎이었으므로 체감 개선의 주된 원인은 초기 대기·메인 스레드 점유 제거와 가벼운 목록이다.

전체 과목 본문을 한꺼번에 준비하는 시간은 늘었다. 분할 자료 검증·Worker 전달·동시 처리 제한의 비용이 있으며, 모든 본문을 가장 빨리 일괄 준비하는 최적화는 아니다. 대신 첫 목록을 이 작업 때문에 기다리지 않고 필요한 과목부터 준비한다. 과목을 지정하지 않은 첫 키워드 검색에는 전체 색인 준비가 필요하다.

원본 첫 방문 중앙값은 낮아졌지만 최댓값은 여전히 7.25초다. 외부 게이트웨이 캐시·네트워크 변동이 있어 코드 변경만의 개선으로 해석하지 않는다. 재방문 원본은 PDF 모듈을 늦게 준비하는 비용 등으로 약 162ms 느려졌다. 미리보기 조작은 먼저 가능하고 저장·변환에 필요한 원본 품질은 유지한다. 원본 대기 45초 초과나 측정 실패는 이번 20회에 없었다.

## 유지보수·재현

프로젝트 루트에서 실행한다.

```sh
npm run build:catalog
npm test
python3 -m http.server 8851 --bind 127.0.0.1
```

다른 터미널에서:

```sh
npm run qa:library
npm run qa:library-state
npm run measure:library -- after
```

`EXAM_SEARCH_URL`로 QA와 측정 대상 URL을 바꿀 수 있다. 측정은 다른 QA와 동시에 실행하지 않는다. `_work/performance`는 로컬 검수 자료이며 배포에 포함하지 않는다. 검수 도구 실행에는 기존 개발 의존성 Playwright가 필요하다.

원본 문항·파일·동의어가 변경되면 `build:catalog`를 다시 실행하고 `data/catalog.json`과 `data/browser/`를 함께 관리한다. 카탈로그만 바꾸거나 자료 파일만 바꾸면 검증에 실패한다. 생성된 상세 자료 50,744,716바이트는 원본의 모든 필드를 보존하며, 가벼운 조회 자료 합계는 8,794,662바이트다. 총 42개 분할 파일이다. 원본 JSON은 개발·검증의 기준으로 남는다. 생성 자료와 카탈로그는 향후 배포 때 포함해야 한다.

1차 검수 당시 카탈로그/자료 캐시는 `exam-library-catalog-v2`, 셰마는 `exam-browser-v2`, 런타임 모듈 버전은 `library-20261008-2`였다. 현재는 2차 개선 문서의 v3 설정을 따른다. 호환성이 바뀔 때는 관련 import와 셰마/캐시 버전을 함께 관리한다.

참고 원본은 읽기만 했으며 이 작업으로 운영 사이트는 변경되지 않았다. 현재 미리보기는 Safari에서 `http://127.0.0.1:8851/`로 열어 두었다.
